# How PI-Lab peers build mobile apps

Of the eight benchmark projects whose mobile source we could verify, **five use Expo and React Native, one uses Capacitor, and two have Apple-specific clients**. The five Expo apps make different choices for the part you touch most. Paseo and T3 Code draw the terminal with native code on both platforms. Paradev puts its terminal in an embedded browser and builds its iOS message composer in Swift. For PI-Lab, I’d keep sharing the server protocol and client state in every option. I’d choose how to build the screens based on which interactions matter most on your iPad, iPhone and S22. This comparison comes from source inspection on November 18, 2026. We did not run the benchmark apps on those devices.

## Which choices fit PI-Lab

**My starting choice would be Expo with React Native for project lists, agent sessions, and navigation.** I’d leave room for separate iOS and Android implementations of the terminal and message composer. T3 Code shows why that can work: fixing Android terminal selection can be a local Android change, while a new session action can still ship to both platforms from one shared screen. Paradev shows the other reasonable priority if replying to agents is the main activity. [T3 terminal interface](https://github.com/pingdotgg/t3code/blob/8cf97b5f06f30a872ce30ab8a888f2ff012365a2/apps/mobile/modules/t3-terminal/README.md) · [Paradev native modules](https://github.com/ParadevAI/Paradev/tree/63b5e28fe6a8cf4a7f124f9f8bf746fd20aec488/apps/mobile/modules)

**Separate SwiftUI and Kotlin/Compose apps are a reasonable option** if the desired differences extend across navigation, gestures, tablet layouts, and text entry. The ongoing cost is deciding and verifying the behavior of each feature twice, even when writing the first version is quick. The two Apple-specific projects show how far to take Apple integration. Neither establishes the cost or benefit of maintaining a corresponding Android app. Capacitor also belongs in the comparison if the team wants to reuse particular web screens. OpenChamber shows that it still takes deliberate work to make those screens suit a tablet. [cmux terminal](https://github.com/manaflow-ai/cmux/blob/main/Packages/iOS/CmuxMobileTerminal/Sources/CmuxMobileTerminal/GhosttySurfaceView.swift) · [OpenChamber layouts](https://github.com/openchamber/openchamber/tree/main/packages/mobile)

## What to test on the iPad and S22

I’d use one real task to choose how much native code PI-Lab needs: open a running agent, read its latest output, select and copy a line, then type and send a reply. On the S22, check Android Back with the keyboard open. On the iPad, resize the app and try a hardware keyboard if available. If the terminal or composer feels worse than the device’s ordinary text controls, compare a native version of that component on the same device. If the gap extends across the whole flow, a fully native client is worth comparing before building the rest of the screens.
